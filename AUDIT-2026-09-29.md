# Stationery Management System — Implementation Audit
**Date:** 2026-09-29 · **Auditor:** Claude Code (live system audit, app running, all flows exercised via API + browser)
**Method:** Code inspection + end-to-end execution of every workflow against the live local build. Nothing is marked complete on the existence of a UI element alone.

---

## 1. EXECUTIVE SUMMARY

The application implements a working core loop on **real university data** (Sept-2026 issuance records migrated at build): teacher kiosk → request with per-person caps → receptionist fulfill/reject → stock deduction at frozen purchase rate → stock-in (manual + fuzzy Excel) → cluster/teacher reports + live charts. This core is genuinely functional and was exercised live (requests #641–#648, stock deltas, 422 cap rejections, undo, keyboard queue).

What does **not** exist yet, measured against the meeting notes: **approval roles** (Cluster Head / Dept Head-Dean — no such users, endpoints, or recorded approver identity), **returns** and **consumption** (the Issue → Consumption → Return model has only the first leg), **SAP integration / Phone→ID** (identity is a hand-typed SAP ID), **guest users** (unmodeled), and **department expense notifications** (reports exist; no expense-triggered alerts).

Four small but user-visible bugs were found and proven: the Excel-upload endpoint is registered with the wrong HTTP method (405), the "Month detail" report renders as a single wrong row (aggregate without GROUP BY), the dashboard low-stock stat undercounts (list capped at 10), and one kiosk message prints a doubled number. Over-issuing beyond available stock is not prevented — it silently clamps to zero.

Rough completion against the 20 requirement sections: ~7 complete, ~6 partial, ~6 missing/needs-clarification, 3 broken elements inside otherwise-working features. The demo of the core request→issue loop is ready today; anything involving approvers, returns, or the two broken report/upload screens is not.

## 5. ACCESSIBILITY / USABILITY AUDIT (concrete)

**Good (verified in-browser):**
- Keyboard-first receptionist: landing on Requests auto-focuses "✓ Fulfill"; Enter acted; focus advances; never stolen from search box. Hint chip visible.
- Kiosk is mobile-first: 56px targets, 2-col grid, one action per card, plain-language caps, undo toast (5s), sticky cart bar, 80px confirmation number.
- Focus rings everywhere (`:focus-visible` 3px); dashboard fits one desktop viewport (measured scroll diff = 0).
- Success/failure states visible: request #, "Queue is clear", cap chips, low-stock badges.
- Destructive-ish reject has no confirmation dialog — defensible for speed, but rejected is **terminal with no undo/reopen path** (a misclick can't be fixed in-UI).

**Problems (each reproducible):**
1. "That's the limit — **1 1** this week." (doubled number, ItemSelector copy).
2. Excel upload of a *valid* file shows "could not parse file" — actually a server 405; message tells the user nothing true or actionable.
3. Reports → "Month detail" shows **1 row** with the month's grand total in the Amount column (₹1,17,364 next to a ₹25 rate) — a normal user would read the report as broken or the data as wrong.
4. Dashboard "Low stock" card showed 10 while 42 items are actually low (list capped at 10; card prints list length).
5. Muted text (`#9aa0b4` on white ≈ 2.9:1) is below AA for small text — affects "by migration", meta lines, item sub-lines.
6. No way for a teacher to check **their** request status or history after leaving the kiosk.
7. Override notifications are silently lost (not persisted) — dashboard under-reports events.
8. Fulfill/Reject records **no actor** — an admin cannot answer "who issued this?" from the system.
9. 424-row Items table and 640+-row Fulfilled list load first 60/all rows with no pagination UI — slow and hard to navigate on the desk machine.
10. Anonymous API calls return 302→405 HTML instead of 401 JSON (kiosk happens to never hit them, but it's a fragile contract).
11. Nav uses emoji icons — acceptable (labels always present) but renders inconsistently across OSes.

## 6. TECHNICAL / ARCHITECTURAL OBSERVATIONS

- **Stack:** Flask 3 + SQLAlchemy 2 + SQLite (single file `backend/stationary.db`), session-cookie auth (Flask-Login), React 18 + Vite (plain JS), recharts, axios. Proxy `/api` → :5000.
- **No run/deploy instructions beyond inference**: `pip install -r requirements.txt` (still an *unpinned placeholder file* — deps were installed ad hoc; versions not locked), `python run.py`, `npm install && npm run dev`. `ProductionConfig` is a stub; no WSGI server, no systemd/docker, no `.env.example` in backend. **Gap for handover.**
- **requirements.txt drift**: lists pandas (unused in code), omits nothing critical, still marked "pin versions after scaffold".
- **Error handling:** custom JSON handlers for 400/404/500; flask-login's default 302 for protected APIs (see §5.10).
- **Data integrity:** single commit per op; append-only request history; deactivation over deletion; StockIn audit trail (426 batches, creator, source). Over-issue clamp is the one integrity hole.
- **Cap engine:** correct per decisions (fulfilled-only, override-excluded, weekly Monday–Sunday); recomputed per item — O(items × 2) queries per kiosk load (fine at 425 items/SQLite, would need caching at scale).
- **Migration:** Sept-2026 rows → 640 fulfilled requests, LEGACY-xxxx SAP placeholders, teachers fuzzy-mapped into 77 clusters — sound, but D-C1 (77 → official ~35) still open; legacy teachers have no real SAP IDs.
- **Frontend:** state is component-local; no global store; cart/selection state lives in RequestForm (lost on navigation — acceptable for kiosk). API layer thin (axios + per-domain modules).
- **Secrets:** dev `SECRET_KEY` fallback in config (fine locally, must be env'd for prod).
